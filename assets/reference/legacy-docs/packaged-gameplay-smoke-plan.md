# M0 packaged gameplay smoke and frame capture — proposal

Status: plan only, prepared against installed Unreal 5.8.3 source on 2026-09-26. No driver or launcher implementation is authorized by this document alone. The first scope is the default Pounce chassis in the real packaged Development build, RainlineReach, seed 2671, standalone/offline. This is a bounded scripted workload, not a general game-playing agent.

## Result to establish

One fresh process performs a repeatable 180-second lower-district scenario through normal controller key processing: movement/look, first mobility use, initial skirmisher combat, shield, weapon, relay A interaction, natural down/wipe recovery, F5 checkpoint retry, first signature use and a return loop. It produces actual world/HUD PNGs, input/outcome records and native engine CSV frame measurements. Both behavior and evidence completeness must pass; a valid timing file cannot turn a failed mission action into a gameplay pass.

The initial rendered mode matches the existing smoke runner: packaged Development, D3D11/SM5, 1920x1080, the project's recorded scalability settings, normal 60 FPS cap, no VSync, `-RenderOffscreen`. This measures an offscreen rendered engine workload, **not on-screen present/display latency or certified playable frame pacing**. A later on-screen run is a separate comparison mode, never mixed into the same baseline. No NullRHI, fixed timestep, time dilation, enemy suppression, artificial damage, health/energy edits, actor relocation, invulnerability or ability bypass is allowed. The only relocation during the scenario is production checkpoint recovery/retry.

## Opt-in and isolation

Use a small `UGameInstanceSubsystem` with behavior compiled out under `UE_BUILD_SHIPPING`, created only with an explicit `-KMGameplaySmoke` flag. Reject simultaneous render-smoke or other harness flags. Installed startup ordering for the current default GameInstance is explicit: `GameEngine.cpp:1267` calls `InitializeStandalone`; `GameInstance.cpp:190–201` creates a dummy world and calls `Init`; `GameInstance.cpp:129` initializes the subsystem collection. Later `UGameEngine::Start` calls `StartGameInstance` (`GameEngine.cpp:1338`) to start the real game. Preflight therefore occurs before the real map's GameMode can save its initial checkpoint. Recheck this chain if a custom GameInstance/startup map loader is introduced.

The proposed launcher creates a fresh GUID directory beneath a fixed project evidence parent and its `User/Saved` directory, verifies physical ancestors/no reparse points, requires the packaged executable rather than editor/bootstrap, and supplies separate `-UserDir` and `-KMGameplayExpectedRoot` arguments. The native preflight compares explicit and engine-derived user/save directories, checks the checkpoint absent through both file path and `DoesSaveGameExist`, and refuses before opening gameplay if isolation is invalid. Merely returning from subsystem initialization or scheduling a graceful exit is insufficient: startup could continue. On an invalid opt-in preflight, log the failure and synchronously terminate only this newly launched test process with public `FPlatformMisc::RequestExitWithStatus(true, 2)` (`GenericPlatformMisc.h:1096`), before real map startup. Normal scenario completion uses graceful exit after evidence flush. No deletion or swapping of player saves or graphics-driver caches.

Only the default local map is allowed; reject travel/connection/listen/host command-line options. After map load require one local possessed player, `NM_Standalone`, no net driver, expected map and fresh mission flags. Abort if these change. The launcher starts only its own bounded process, records its PID and exit status and may stop only that process at timeout. Proposed total timeout: 300 seconds (startup up to 60, scenario 180, CSV/screenshot flush up to 30, remaining cleanup margin). All injected keys are released on every failure and teardown. An unexpected physical input event should mark the run contaminated rather than silently becoming part of its scripted result.

## Actual input path

Installed UE 5.8.3 provides the non-deprecated `APlayerController::InputKey(const FInputKeyEventArgs&)` (`PlayerController.h:1791`, implementation around `PlayerController.cpp:2407`). Construct events with `FInputKeyEventArgs::CreateSimulated` from `InputKeyEventArgs.h:135`; use the local player's mapped input device from `IPlatformInputDeviceMapper::GetPrimaryInputDeviceForUser`, rather than assuming device zero. Controller filtering checks that ownership.

Resolve movement, fire, shield, mobility, signature and interact keys through `AKMMechCharacter::GetKeyboardBinding` and record them. Emit separate pressed/released events across real frames; retain held-key state until release. Release every held digital key and clear axis input on every phase transition, failure and quit; the next phase explicitly establishes its own inputs. Emit analog MouseX/MouseY events for look, with bounded increments and their true delta/sample fields. Installed `UPlayerInput::InputKey` mirrors these scalar inputs into their paired axes, so the existing Mouse2D Enhanced Input mapping processes them. Supply inputs on `OnWorldPreActorTick` before player processing; observe outcomes on subsequent ticks, taking care to pair observations with their preceding time interval.

Use a small heading/waypoint controller driven by observed pawn position and camera/control rotation. It may read enemy and objective transforms to aim, but it may not call `SetControlRotation`, `AddMovementInput`, `TeleportTo`, protected fire/shield functions, `ExecuteMechAbility`, GAS direct activation, interaction interfaces, GameMode mutation, damage application or direct retry. Aim is achieved through mouse-axis events; movement through mapped keys. The initial deploy menu is closed with an Escape key event and must actually disappear. F5 must traverse the existing controller binding. No direct `CloseDeployMenu` fallback: a missed input action fails its stage.

This tests the controller/PlayerInput/Enhanced Input mapping path. It deliberately bypasses physical devices, OS event delivery and Slate pointer targeting; it makes no human input, gamepad usability or input-latency claim. A `true` return from `InputKey` alone is not acceptance; the corresponding world outcome is required.

## Fixed 180-second scenario

Times are wall-clock offsets from the native CSV first-captured-frame callback. Transitions require the preceding outcome to be proven; clock expiry alone never advances a failed action. Use the listed maximum deadlines; finishing early retains an explicitly logged idle/guard period until the next boundary. Do not extend a phase until it passes or omit idle frames. Missing a required outcome fails the run explicitly; only a fully completed scenario earns the 180-second acceptance. Record simulation time separately. The precise waypoint geometry and initial input gains must be validated in one diagnostic run before considering this a stable repeatable benchmark.

The current Pounce supports the mapped shield: `ServerSetShield_Implementation` at `KMMechCharacter.cpp:290` has no Bastion restriction, and the directional mitigation in `TakeDamage` applies to either chassis. Bastion alone blocks firing while shielding. Pounce's signature grants three timed free mobility charges (`ExecuteMechAbility`, around lines 385–391); the proposed check observes that supported effect, not Bastion shelter behavior.

This schedule is a proposed workload, not a promise the current AI makes every deadline. If pursuit/combat stalls, capture the failed stage and diagnose the actual game or driver. Never silently shorten a path, teleport, kill a guard or waive a required outcome. If the scripted movement itself cannot meet its defined deadlines, revise/version the scenario deliberately and rerun from the start; do not compare different scenario revisions as equivalent performance runs. Deliberately accepting hostile damage and driving inputs automatically makes this a reproducible stress/smoke sample, not representative average player behavior or a measure of fun.

## Native timing and first-use evidence

Use `#if CSV_PROFILER` and `FCsvProfiler` from `ProfilingDebugging/CsvProfiler.h`. `BeginCapture(-1, destination, filename, ECsvProfilerFlags::None)` is public at line 519. Subscribe before starting to `OnCSVProfileFirstFrame` (line 558) and anchor the 180-second scenario there; do not begin input while capture startup is pending. Record phase/action/outcome markers with `CSV_EVENT_GLOBAL` and include build/scenario settings through `SetMetadata` or `CSV_METADATA`.

At completion call `EndCapture()` (line 529), retain its `TSharedFuture<FString>`, poll readiness without blocking the game thread, and wait for the returned file path / `OnCSVProfileFinished` before quitting. Do not mistake `EndCapture` request or a partial file for completion. Delegate handles must be removed during teardown. Missing CSV support is an explicit failed measurement gate, never replaced with actor Tick delta.

Installed `CsvProfiler.cpp:4369–4388` defines the normal `FrameTime` stat from monotonic platform timestamps after engine max-tick-rate waiting; it records milliseconds and includes the pacing wait. Keep this native metric's identity. It is not interchangeable with simulation delta, game-thread work time, GPU work time, or display present intervals. Preserve any additional native game/render/GPU columns actually present; do not invent unavailable metrics.

Start capture before first mobility, weapon, shield and signature actions. Mark each first input and first observed result, plus screenshot requests and natural recovery. Do not prewarm these actions, discard startup-action spikes or filter idle periods. Call this **fresh-process first-action evidence**: user-directory freshness does not prove the GPU driver, OS file cache, shader cache or cooked PSO cache is cold. Normal game asset preloading remains part of the production path; earlier process/map startup is recorded in launch logs separately from the 180-second gameplay window.

Retain the unmodified native CSV and its SHA256. A separate converter must recognize actual engine headers, frame rows and metadata/footer structure from the first captured file; validate the exact FrameTime column, units, positive finite values and row accounting. Do not feed an assumed native layout into the simple existing analyzer or drop malformed/nonfinite samples. Every frame in the capture remains in the aggregate, including menu/idle/screenshot overhead. Report the exact capture interval and any boundary frames separately; phase-level summaries are supplementary, never substituted for the full-run statistics.

Report mean FPS derived from measured frame times, p95/p99/worst milliseconds, count over 50 ms, duration/sample count and first-use event neighborhoods. `Tools/Analyze-FrameTimes.py` may process a verified normalized export once its input contract is met; its 30-minute flag will correctly remain false. Keep its timing target separate from gameplay correctness and the offscreen presentation limitation. A three-minute success cannot certify flawless runtime or sustained thermal/memory/network stability.

## Images and run receipt

Use `FScreenshotRequest::RequestScreenshot(fullPath, true, false, false)` (installed `UnrealClient.h:219`) to capture the actual viewport/HUD. Serialize requests and verify complete PNG decoding/dimensions after the corresponding request finishes. Proposed milestones: initial deploy/menu, first mobility landing, shield hit, initial enemy defeated, relay A checkpoint, downed state, recovered state, first signature, final loop/idle. Capture requests do not pause or fast-forward gameplay. Their readback/write overhead stays in the frame statistics and is annotated; use the same milestone policy for compared runs.

Write a manifest with package executable/module/content hashes, engine/build configuration, scenario revision/hash, GPU/driver/CPU/RAM, renderer, resolution, actual scalability, frame cap/VSync, window/offscreen mode, seed, user/save paths, bindings and process start/end times. The action log records press/release/axis events and subsequent observed outcomes. World samples record pose, health, energy, cooldowns, enemy counts/identity, mission flags, serial and checkpoint restore events. Save milestone receipts and all failed-stage diagnostics. An overall PASS requires every mandatory outcome, native CSV completion, exact fresh PNG inventory and an uncontaminated run; never synthesize missing screenshots or timing records.

The performance-optimization skill was read for this proposal. Its optimization workflow begins after a reproducible scenario emits a stable metric; that prerequisite is not yet met. No game-dev CLI availability, sealed/admitted measurement bundle, optimization loop, comparison result or hardware-performance pass is claimed here. After the driver succeeds, repeat the same version in fresh processes and assess workload comparability before considering optimization work.
