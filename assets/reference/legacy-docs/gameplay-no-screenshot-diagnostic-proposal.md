# Screenshot-disabled diagnostic proposal

Plan only; no implementation or engine run. Keep Gameplay08 and the unchanged Package04 repeat immutable. Their `lower-pounce-v2` visual-evidence validator remains unchanged.

The question is whether the11 PNG completion-associated stalls persist when the driver never requests pixel readback or PNG encoding/saving. This isolates the screenshot mechanism as a controlled diagnostic variable; it does not certify a better production build or replace visual acceptance.

- Use a separate explicit opt-in capture policy and scenario identity, for example `lower-pounce-v2-no-screenshot-diagnostic-v1`, recorded in launch manifest, native CSV metadata and receipt. No silent fallback or reuse of the visual scenario name. The normal policy stays the default and still requires11 valid PNGs.
- Retain the same native package code, map, seed, input controller policy, gameplay/state outcome requirements, renderer, settings, offline isolation, real AI,180-second interval, original phase deadlines and continuous Lit/Lighting/no-ShaderComplexity checks. A future combined build should expose both policies so any causal comparison uses the same executable/content hashes; Package04 versus a modified binary alone is not a clean one-variable comparison.
- At each of the existing11 visual milestones, record an explicitly named `image_omitted_by_diagnostic_policy` intent with its original milestone name and time. Do not request FScreenshotRequest, enqueue a PNG, synthesize a processed callback, increment completed-images, or create placeholder images. The diagnostic path must not wait for nonexistent image completion. Reject any unexpected screenshot request or PNG file during the run.
- Require0 actual screenshot requests,0 processed images,0 PNG files and exactly11 ordered omission intents in a distinct diagnostic validator. Retain all original mandatory gameplay outcomes, spacing/combat proof, two recoveries, patrol loops and full native frame/render-state accounting. Return `passed_nonvisual_capture_overhead_diagnostic`; it must never return visual acceptance. Keep both the raw native CSV and every frame in its statistics, including startup/frame0, first actions and idle frames.

“Same input” means the same closed-loop input policy and required outcomes, not identical timestamped key events. Removing a synchronous stall changes the number/timing of real simulation updates, and the existing menu/relay image-completion gates disappear in this explicitly different diagnostic policy. Log those action/waypoint/encounter timing differences and compare actual outcomes and combat counts. Do not insert artificial delays or fabricated image completions to disguise them. If the route, encounter count or required outcomes differ materially, report that confound and do not attribute the entire timing difference to PNG work.

After review, run matched fresh-process pairs using the same build and instrumentation except capture policy, preferably alternating order and repeating once. No cache clearing or prewarming. Compare full-run FrameTime distributions, count above50ms, worst frame and startup separately as a diagnostic annotation—not as excluded samples. Inspect neighborhoods of the same milestone intents and ensure both runs complete the identical logical objectives. A drop localized around omission intents would support screenshot-mechanism contribution; persistent stalls or broad gameplay changes would require the more detailed CPU/readback/compression/file-write tracing proposed in the hitch report.

The next implementation would be limited to the opt-in harness, launcher, separate policy validator and regression fixtures; no camera, combat, AI, collision, rendering-quality or health change. Independent critic approval precedes implementation. Normal visual acceptance and its performance targets remain intact.
